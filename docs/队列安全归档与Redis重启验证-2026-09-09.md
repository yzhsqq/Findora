# 队列安全归档与 Redis 重启验证

2026-09-09，本轮将 ACK 后永久增长的 Stream 消息改为可人工执行的安全归档，并实际验证官方 Redis 7.4.8 的 AOF 强制重启恢复。默认不自动清理，操作员先 dry run，再显式 apply。

## 清理规则

`scripts/queue_maintenance.py` 分页扫描普通流、大请求流与 DLQ。只有 done/failed、有可信 terminal_at、超过保留期限且所有消费组的 last-delivered-id 已越过该条目、该条目不在任意 PEL 中时才可清理。queued/running/retrying、未读、未 ACK、旧版本无 terminal_at 的记录都保守保留。

完整任务结果与原始消息先提交到 `DATA_DIR/queue_archive.db`。随后 Lua 再次核对原状态版本、消费组和 pending，确认无竞争变化才将 Redis 状态换成小墓碑并对明确的 message ID 执行 XDEL；不使用可能删除 pending 的 XTRIM。归档提交失败不会删除 Redis 数据，归档后重新进入 pending 也不会删除。

墓碑永久保留 task_id、业务内容指纹、终态、时间与来源信息，阻止相同 request_id 的历史请求重新执行。`RedisStreamTaskQueue.get_status()` 从 SQLite 恢复完整原结果；归档不可用时明确报错，不返回空的成功结果。API/worker 已在 composition 接入相同归档文件。

DLQ 也先归档原消息与死信内容，再检查源流及 DLQ 自己所有消费组是否完成；只有源消息和死信都移除才释放每条消息的 DLQ 去重标记。没有建立 DLQ 消费组时，可按期限归档供人工审计。统计中的 deleted 表示本轮删除的扫描主体数，一条 DLQ 连带删除其源条目仍记 1。

## 运维命令

从工程根运行，使用当前环境的 REDIS_URL 与 DATA_DIR：

```bash
uv run python -m scripts.queue_maintenance --older-than-days 7 --limit 1000
uv run python -m scripts.queue_maintenance --older-than-days 7 --limit 1000 --apply
```

apply 成功后保存每流游标到 `DATA_DIR/queue_maintenance_cursors.json`，下一次继续分页；到末尾回到起点，以便再次检查之前未满足条件的记录。dry run 不写游标。可由已有运维调度周期运行该命令。命令只打印数量和游标，不把商品需求或回复打印到日志。queue metrics 记录实际成功的新增、状态转移、死信与归档删除，不携带任务、会话或买家标签。

必须同时备份 Redis AOF/RDB 与归档 SQLite；墓碑仍永久增长，但体积不再包含长回复。归档文件目前无自动 TTL，清除它会使对应历史结果不可读。非终态状态仍为一小时 TTL，超长排队不属于本次终态 retention 保证；业务幂等仍依赖持久交易确认。SQLite 归档使用本机共享 DATA_DIR，不代表多主集群外部归档服务。

## 实际验证

```bash
FINDORA_REDIS_SERVER_BIN=/tmp/globex-redis-build/redis-7.4.8/src/redis-server \
  uv run python -m pytest -q \
  tests/test_queue_redis_restart.py tests/test_queue_retention.py \
  tests/test_queue_reliability.py tests/test_phase4_queue.py \
  tests/test_queue_api.py tests/test_harness_infra.py \
  --junitxml=/tmp/globex-queue-retention-tests.xml
```

实测 **54 passed in 5.32s**。新增 6 项 retention 测试均启动隔离真实 Redis 并写真实 SQLite：双流归档与完整结果恢复、所有消费组 ACK 条件、归档磁盘故障保留 Redis、归档后真实 XCLAIM 重建 pending 的竞争、DLQ 审核消费组与坏 payload 归档、旧记录和归档丢失失败关闭。

另 1 项强制重启测试启动独立 Redis，配置 `appendonly yes`、`appendfsync always`、`port 0`、仅权限 700 Unix socket；普通/大请求流各领取一条留在 PEL 后对 Redis 进程发 SIGKILL，再用同目录 AOF 启动新进程。确认原 message ID、consumer 与投递次数保留；真正 consumer.consume 从两流 reclaim，deliveries=2，成功后 pending 清零。此测试没有优雅 SHUTDOWN，没有连接或清空用户已有 Redis。

验证范围是单节点 AOF 强制重启，未验证 Redis Cluster、多主故障转移、网络分区或生产磁盘故障。缺少 Redis 二进制会明确 skip，不能将 skip 当成真实验证通过。
