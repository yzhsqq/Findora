## 3. 各工作包怎么实现

### 1）P0：交易确认、操作幂等与库存原子性

**证据**：[order_tools.py](../app/application/tools/order_tools.py#L39) 创建工具只接收商品与地址；[permissions.py](../app/application/agents/permissions.py#L17) 放行业务写工具；[order_usecases.py](../app/application/usecases/order_usecases.py#L29) 没有业务操作键，订单保存位于库存回滚保护之外。查询/取消 UseCase 也没有买家归属参数。

**实施顺序**：

1. 从 9 月方案取最小 `ShoppingTaskState`：当前候选及版本、已选 SKU、数量、约束作用域、订单引用。增加 `PendingConfirmation`，持久化报价/地址/数量摘要、版本、有效期及确认来源。
2. 用户表达确认时绑定当前快照；工具执行只引用该确认记录，并由服务端验证。价格、数量、地址变化使旧确认失效。验证已有确认，不增加同一操作的重复询问。
3. 给每次业务操作生成稳定 `operation_id`，在数据库建唯一约束；同一操作重试返回已有结果。不要以“商品相同”或“问句相同”判断重复购买，否则会拦住用户再次购买。
4. 将库存、订单与操作记录纳入同一个事务，使用条件扣库存和并发安全的订单 ID。取消同样原子执行且只回补一次。课程规模可先沿用 SQLite，无需先迁移数据库产品。
5. 查询/取消核验订单 owner；会话、任务和 WS 订阅绑定身份。当前入口接受请求体中的 buyer_id，真实多买家环境还需可信身份接入；本地 demo 身份模式应明确标识。

**验收**：旧确认、跨会话确认被拒；压缩/重启后确认仍绑定正确商品；同操作并发重试仅一单；保存失败库存不变；取消重试仅一次回补；不同买家不能查询或取消他人订单。

**本轮已复现**：纯内存环境中模拟订单保存失败，库存从 50 变 49，未回滚；两次相同参数调用生成两个订单，证实 UseCase 没有操作去重机制。后者不是要求禁止正常再次购买，而是需要显式操作 ID 区分重试。

### 2）P0：任务执行可靠性与全局配额

**证据**：[redis_stream_queue.py](../app/infrastructure/queue/redis_stream_queue.py#L127) 只读新消息；`claim_stale` 在第 198 行定义但没有接入调用，还只处理普通流并丢弃 message_id。[SessionRegistry](../app/application/agents/main_agent.py#L162) 只有实例缓存及直接覆盖保存；[server.py](../app/presentation/server.py#L277) 收到会话内任意最终事件即返回。[GatewayThrottle](../app/infrastructure/throttle.py#L20) 使用进程内 semaphore。

**实现**：

- 两条流都定期 reclaim，保留 stream、message_id、投递次数，复用处理、ACK 和死信逻辑；区分可重试故障和终态业务失败。
- 同一会话串行；多 worker 通过会话 lease/fencing 或固定分片保持单一执行者，快照用 revision/CAS 防止覆盖。恢复执行前读取最新状态，避免另一 worker 的旧缓存覆盖新上下文。
- 每轮贯穿 request_id/task_id，HTTP 等待、事件、任务查询和前端均按任务匹配；不能只靠 session_id。
- 扩 worker 之前补共享并发租约与请求速率限制；以网关实际配额维度管理，流式请求到结束才释放。增加 worker 不应成倍放大上游配额。

**依赖与验收**：先完成第 1 项的写操作幂等，再开启自动重投；处理中杀 worker，两条流都能恢复；超限进入死信且状态可查；同会话并发不串答、不丢状态；多 worker 总在途模型请求不超配额。

### 3）P0：完成已选定的 Langfuse + Trace 方案

**初始审计时现状**：[tracing.py](../app/infrastructure/tracing.py#L30) 已有 OTLP/HTTP exporter 和 Agent 中间件。当时任务载体 [IntentTask](../app/domain/queue/ports/task_queue.py#L24) 未携带 Trace 上下文，代码未形成业务请求贯穿链路；这一实现缺口随后已补齐，当前验证边界见总表。

**纠正历史判断**：本次读取了已安装的 `OTLPSpanExporter` 源码，它会自动读取 `OTEL_EXPORTER_OTLP_HEADERS` / `OTEL_EXPORTER_OTLP_TRACES_HEADERS`。因此“不显式传 headers 就绝对接不上 Langfuse”不成立。真实缺口是配置说明与透传、跨进程关联、语义字段及验证证据。

**实现**：复用现有 OTLP 路线，补 endpoint/认证配置和 app、worker 的 Compose 透传；显式声明应用直接依赖的 OTel 包；在 API 建立请求 span，通过队列传递标准 Trace 上下文，在 worker 恢复，并关联日志、事件、session/task。业务 request_id 与 OTel trace_id 含义分开，不能仅生成一个随机字符串就宣称跨进程 Trace 已打通。对模型/工具补输入输出摘要、模型、token、错误和耗时等可检索属性。

Langfuse 的 OTLP 地址、Basic Auth 和当前接入要求以[官方 OpenTelemetry 文档](https://langfuse.com/integrations/native/opentelemetry)为准。沿用用户已选的 OTLP 方案，不要求为了接入重写所有埋点。

**验收**：单测验证配置和上下文传播；本地 HTTP 接收端证明请求确实导出且路径、认证正确；最后在真实 Langfuse 验证跨 API/worker 的父子关系和可检索字段。本地接收端通过只能证明传输，不能替代 Langfuse 看板验收。未配置时主业务正常，导出失败可观测且不拖垮业务。

**验收**：生成商品、知识、Agent 三份可追溯正式报告。沿用当前 `online-main` 的 Recall@8 ≥ 0.90、MRR/NDCG@8 ≥ 0.85、无结果及硬约束准确率 1.0；发生降级必须阻断。Precision 在金标未穷举时继续作为观察项，不能恢复旧文档的硬阈值。关键词降级链使用其独立批准基线，不与主链混判。

### 6）P1：上下文治理与预算最终兜底

**来源**：[9 月上下文方案](research/Claude-Code上下文管理与Findora结合方案.md#L550)，以及清单中预算 fallback 的已知限制。现有自动摘要与偏好管理已经实现。

**实现顺序**：

1. 商品等大工具分离完整原始结果与 LLM 决策投影；原始结果进事件/存储并提供 result_ref，模型只接收必要字段；子 Agent 回传采用可校验的结构化决策结果。
2. 基于第 1 项权威状态组装上下文，先清理旧工具结果，仍超预算再摘要。摘要保存理由、未决问题与引用，精确金额/ID/确认状态从权威记录恢复。
3. 增加 `conversation_fact_lookup`，按会话和证据引用定点回查；持久化偏好 revision 与已注入版本，撤回、压缩、重启后确定性重注入。
4. 修正 `TOOL_RESULT_LIMIT` 的 token 单位说明；记录压缩前后 token、耗时、摘要版本、cached token、TTFT 与成功任务成本。
5. 预算不足时从已验证结果生成规则回复，停止新增模型调用与派发；并行任务在调用前预留预算，执行后按实际 usage 结算。

**验收**：压缩前后 SKU/订单/金额/硬约束保真；“第二个”指向最新候选；一次预算不误带到下一任务；撤回偏好不被旧摘要恢复；耗尽后新增模型调用为 0。缓存收益先测量，显式缓存后置。

### 7）P1：Hybrid 召回及索引版本更新

**证据**：[catalog_search.py](../app/application/usecases/catalog_search.py#L116) 当前是向量成功后精排，失败或空结果再用关键词；关键词评分只是交集计数，并非 BM25/RRF。硬约束在固定 topN 之后过滤，可能错过更深的合规候选。[category_knowledge.py](../app/infrastructure/rag/category_knowledge.py#L210) 遇到已存在 document_id 即跳过入库。

**实现**：新增关键词召回端口，先在当前 500 SPU 规模实现可维护的 BM25，和向量并行召回→RRF→同款去重→现有 reranker；可表达的硬约束下推或适应性补召回，最后仍做统一过滤。索引记录内容 hash/版本，知识更新替换旧 chunk，删除同步清理；无需先引入大型搜索集群。

**验收**：在第 4 项冻结基线上比较型号/品牌/中文实体词与语义 query 的分桶收益，同时观察延迟；不预先承诺效果提升。硬约束仍 100%，知识文件同 ID 更新后只召回新版本。

### 8）P1：指标、告警与分数回注

这部分是历史中发现的遗漏，但超出上次只选定的 Langfuse A 范围，应作为后续独立工作包。

**实现**：在现有中间件和队列边界输出请求/工具数量、P95/P99、错误/降级率、队列等待/积压/死信、模型总并发、token 与成本；增加 `/metrics` 或等效统一出口。指标标签使用有限维度，task/trace ID 留在日志和 Trace。告警先进入事件和日志；评测分数通过 Langfuse 支持的评分 API 回注到对应 Trace。

**验收**：注入工具超时、队列积压、模型限流可观察并触发对应告警；重复跑评测不会错误关联分数；仪表盘能定位到具体任务的证据。

### 9）P1：Bad Case 最小闭环

**实现**：复用 ConversationStore，从工具异常、空召回、断言/漂移、用户负反馈采集候选；关联 task/trace、Prompt/模型/数据版本；去重、脱敏、人工归因后进入开发回归集。发版集按规则独立冻结，不直接把未审核模型判断当金标。先做脚本/简单审核入口即可，不必先建复杂平台。

**验收**：选一条真实或注入失败，完整演示回收→复现→标注→修复→回归；每条样本可以找到输入与工具证据。

### 10）P2：Prompt 版本化与 A/B

**实现**：从固定 `globex.yml` 升级为不可变版本记录，绑定内容 hash、工具集合和发布时间；先离线成对评测，再按买家稳定分组，会话固定版本。版本贯穿 Trace、流水和缓存，支持回滚。

**依赖/验收**：依赖第 4、8、9 项；比较任务成功率、硬约束、成本与延迟，不能只比较 Judge 总分；同会话不跳版本、版本间缓存不混用，任何 P0 回归都阻断发布。

### 11）P2：Agent Skill 渐进加载

**实现**：先制作少量人工维护的能力包，例如选型流程、跨境规则查询流程；常驻轻量元数据，命中后按需加载正文和工具白名单，记录版本与加载事件。继续按现有 DDD 分层落位，无需为了匹配教程文件名重构目录。

**验收**：未使用时不注入完整正文，加载不越过工具权限；通过同集对比证明上下文成本或成功率收益。

### 12）P2：成功策略记忆与自进化

**实现**：依赖经过审核的 Bad Case 和成功轨迹，提炼带适用条件、证据来源、版本、失效时间的策略；独立于买家偏好存储，受限检索后注入。先人工审核发布，再评估自动化。

**验收**：能追溯、撤销；错误策略能下线；不得覆盖买家 dislike、预算等硬约束；固定评测集上的任务收益足以覆盖新增成本。

## 4. 有条件后置的设计

- **Semantic 单步断言**：目前只有 Schema/Sequencing 的实质实现，轻量模型语义判定未接。先根据坏例确定检测对象，做离线或异步采样；证明收益后再考虑同步执行，避免每个工具都额外调用模型。
- **显式 Prompt Cache、自适应压缩阈值、压缩抖动检测**：9 月方案明确要求数据证明后再做。先拿到隐式 cached token、工具输出 P99、TTFT 和成功任务成本，再决定投入；不能将其他模型平台参数直接复制给当前网关。
- **结构化可点击确认卡**：按用户新增前端要求，已移入第 5 项正式交付范围，与第 1 项的确认凭证协同实现，不再作为后置可选项；不重复询问已有效确认的同一操作。
- **大规模真实供给、点击/加购日志、K8s、vLLM、训练侧能力**：属于规模或生产目标扩展，当前不能仅因教程提及就当作必做欠账。

## 5. 交付节奏和验收方式

1. **第一批：正确性、前端体验和证据。** 第 1/2 项按交易幂等→重投顺序落地；第 3/4 项可并行。第 5 项先定视觉与 AG-UI/数据契约，然后交付真实联通的新页面；重放与确认依赖第 1/2 项，一并作为本批完成条件。
2. **第二批：效果和成本。** 以冻结基线推进第 6/7 项，同时建设第 8/9 项；每次变更独立评测，能判断提升来自哪里。
3. **第三批：实验和扩展。** 先版本化再 A/B，先人工 Skill 再策略自进化；只有指标证明收益才扩大范围。

每个工作包都同步更新 README、教程对应章节和《教程实现对齐清单》，分别标注“设计完成”“代码完成”“本地验证”“真实依赖验收”，避免把存在接口或历史测试记录写成当前已完成。

测试按变化选择：领域/事务/队列故障回归；真实 Redis/Qdrant 和模型的主链联调；并发阶梯测试与多 worker 总配额检查；前端断线/重复结果/空检索浏览器验收。压测报告记录实际网关额度、并发数、错误率、P50/P95/P99、吞吐和成本，不以一次旧的 2/5/10 并发记录替代新变更验收。
