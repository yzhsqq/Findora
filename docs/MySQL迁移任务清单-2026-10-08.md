# MySQL 迁移任务清单（2026-10-08）

依据：全量更换 MySQL 的分级分析（见会话）。目标是把 SQLite 的快照层与业务库迁到 MySQL 8，保留中文商品检索与变体检索的正确性。每项通过验收后更新状态；未执行的外部验收保持未完成。

## 执行规则

- 不操作真实商品库、旧数据库或运行中的服务；迁移行为在隔离数据上验证。
- 数据相关改动优先保证旧数据可见、失败不覆盖、冲突明确拒绝。
- 先做数据安全（列类型、备份），再做功能正确（检索重写），最后做机械改写。
- 每项保留问题编号、变更范围和验证结果；迁移前先落 Alembic，schema 从此版本化。
- 本机 MySQL 实例的启动方式（原生 / Docker）须用户批准后确定，未定前 P0 环境项视为阻塞。

## 实施进度（2026-10-08 第二轮：M07 / M08 完成）

热路径两端（findora.db、ag_ui_runs.db）已全部迁入 MySQL `findora` 库，逐行校验零差异；全量回归 1190 passed / 43 skipped / 0 failed。

**本轮实测发现的三个问题**（均为"SQLite 能跑、MySQL 出错或退化"，编译期不可见）：

1. **浮点列被建成了 4 字节 FLOAT**。SQLAlchemy 的 `Float` 在 MySQL 上映射为 `FLOAT`（单精度），而 Unix 秒已到 1.79e9，float32 在该量级只剩约 128 秒分辨率。受影响列：`agui_runs.created_at/lease_until/updated_at`、`agui_sessions.updated_at`、`context_operations.deadline`。其中 `lease_until` 直接参与租约过期判断，偏差会到分钟级——这是正确性问题，不是精度洁癖。已全部改为 `Double`（SQLite 侧仍是 8 字节 REAL，行为不变），相关表已重迁并重新校验。
2. **MySQL 8.0.20+ 的 `VALUES(col)` 已废弃**，每次 upsert 都发警告。已改为行别名形式 `VALUES (...) AS new ... new.col`（需 8.0.19+，本机 8.0.45 满足）。
3. **SQLite 日志引擎的连接池化会放大写锁竞争**。改用 `NullPool`（每次操作新建并关闭连接，与原实现一致）：同一文件上不再长期并存多条池化连接，并发写入的等待时间由 10 秒级回落到毫秒级。同时补了取锁重试——SQLite 在写锁与提交交错时可能直接返回 `SQLITE_BUSY` 而不等待，重试只包住 `BEGIN IMMEDIATE` 这一步（用户代码尚未执行，重试不会重复写入）。

## 实施进度（2026-10-08 第三轮：trade_store 事务语义迁移完成）

`trade_store` 是切库前最后一道坎，其幂等保证从"SQLite 整库写锁"迁到"InnoDB 行锁 + FOR UPDATE + 唯一索引"，SQLite 路径行为不变。全量回归 1190 passed / 47 skipped（+4 项 MySQL 并发契约）/ 0 failed。

**迁移要点**：

1. **`resolve_confirmation` 对确认行加 `SELECT ... FOR UPDATE`**（只对 MySQL；SQLite 方言忽略 FOR UPDATE，仍由 `BEGIN IMMEDIATE` 兜底）。锁已存在的行，串行化"同一确认并发决议"，否则两个事务都能读到 `pending`、都去建订单，产生两笔订单。
2. **`prepare_confirmation` 靠 operation_id 唯一约束 + 撞键回滚重读**。并发"读-再插"在 MySQL 用间隙锁会**死锁**，故不预先加锁：插入撞唯一键时 `rollback` 后重读（SQLAlchemy 下次查询自动开新事务、取新快照，能看到对方已提交的行），走幂等分支返回。SQLite 下该分支不可达（`BEGIN IMMEDIATE` 已串行化）。
3. **建表按方言分流**：`initialize_inventory` 抽成 `_ensure_schema`，SQLite 用 `BEGIN IMMEDIATE` 串行化 checkfirst，MySQL 用重试（容忍 checkfirst 与 CREATE 之间的并发 "already exists"）。
4. **整数宽度对齐**：`trade_tables.py` 的 `stock`/`unit_price_minor` 从 `Integer` 改为 `_BigInt`（MySQL BIGINT）。校验上限是 2^63-1，而 MySQL 的 INT 只有 32 位，金额以最小货币单位存储时溢出是静默损坏。`trade_sku_inventory`（705 行库存种子）已 drop 重迁为 BIGINT。

**验证**：新增 [tests/test_trade_store_mysql.py](../tests/test_trade_store_mysql.py)，仅当设置 `MYSQL_TEST_URL` 时运行，自建独立临时库不触碰 findora。覆盖四个并发契约：同确认并发决议只产一笔订单、同 operation_id 并发 prepare 幂等、不同操作抢最后库存一胜一 INSUFFICIENT_STOCK、并发取消只恢复一次库存。本机 `MYSQL_TEST_URL="mysql+asyncmy://root:PASSWORD@127.0.0.1:3306"` 下 4 项全绿，未设 URL 时 4 项跳过（CI 无 MySQL 不受影响）。

**3. 本轮实测发现并修复的一个问题（编译期不可见，且极易误诊）**

**eBay 迁移在 1MB / 512KB 分片下必挂，报错形似字符集问题，实为 asyncmy 读缓冲 bug**。完整堆栈有两层：

```
asyncio: Fatal error: protocol.buffer_updated() call failed.
  asyncmy/connection.pyx get_buffer → BufferError: Existing exports of data: object cannot be re-sized
asyncmy/protocol.pyx _parse_row → UnicodeDecodeError: 'utf-8' codec can't decode byte 0xfc
```

第二层的 `UnicodeDecodeError: 0xfc` 极具误导性——它看起来就是 latin1/utf8mb4 转换问题，但实测服务端 `character_set_client/connection/results/server` **全部 utf8mb4**，`max_allowed_packet`=64MB 也未超限。真相是：读缓冲 resize 失败后协议错位，后续行解出垃圾字节，`0xfc` 是垃圾不是 latin1 的 ü。**改 charset 无效，只能缩小读回分片**。

阈值是用 eBay 真数据二分实测出来的（`1024KB/512KB → 失败；256KB → 924 行全过`），`_CHUNK_BYTES` 由 1MB 收紧到 **256KB**（对失败点留 2 倍余量）。注意单列最大 386KB 也能过，说明触发条件是**分片累计字节数**而非单行大小。

顺带修正第五轮的一个判断：第五轮定的 1MB 只是"CJ 数据刚好能过"，不是安全阈值。

### 裁剪任务与理由

- **M11（移除 lock 补丁）**：SQLite 快照仍被采集 / 报价脚本使用，`BEGIN IMMEDIATE` 是 SQLite 下唯一的写锁提前获取手段；本地化库也保留 SQLite，故锁逻辑继续保留。

### 关于 M12 / M13 的现状

`cj_catalog.py` 的变体匹配已在 SQLite / MySQL 双分支分流：SQLite 走 `json_each`（保留 `COLLATE NOCASE` 冻结行为），MySQL 走 `JSON_TABLE`（`_variant_match`）。因此直接 pid / SKU 查询在 MySQL 上无需独立 variants 表也能命中（CJ 7/7 用例含精确与小写 SKU 已验证）。M12（variants 拆独立表 + 索引）与 M13（其余 JSON1 用法改写）未做，如需为变体检索单独加索引再排期。
