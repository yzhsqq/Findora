### M09 遗留的两个事实结论（M10 会用到）

1. **真实 `products` 表是 19 列，不是 spec 说的 12 列**：`sync_cj_catalog.py` 原始 DDL 12 列，`cj_enrichment` 采集阶段又 ALTER 追加 7 列（`source_url*` / `enrichment_attempted_at`）。为不静默丢数据，M09 的模型扩到 19 列。→ 意味着 M12（拆 variants）设计时也要以**真实 schema** 为准，先 `PRAGMA table_info` 看实际列，别只信 DDL 源文件。

## 6. 铁律 / 坑（接手必读）

1. **密码不进仓库**：本机 MySQL 密码 **绝不能**写进任何提交的文件（含 md/py/txt）。凭据只从 `mysql_url` 参数或环境变量读。文档与测试里一律用 `root:PASSWORD` 占位符，实测时用 `MYSQL_TEST_URL` 环境变量注入。
2. **pytest 运行参数**：Windows `%TEMP%\pytest-of-哈哈` 无写权限会 `WinError 5`，必须加 `--basetemp=.pytest-tmp -p no:cacheprovider`（或按需换 `.pytest-<name>`）。MySQL 门控用例未设 `MYSQL_TEST_URL` 时自动 skip。
3. **asyncmy 大结果集 bug**：读缓冲 resize 会抛 `BufferError`（表现为 `(2006, 'MySQL server has gone away')`），`max_allowed_packet` 64MB 未必超限。**大 INSERT/读回语句按 ~1MB 切小片**，提交边界仍保持 1000 行 / 64MB。
4. **Windows GBK 控制台**：中文日志输出可能乱码，是显示问题不是数据问题，不影响校验。
5. **本地优先**：改动先在本地验证；Docker 只在最终集成用，且**需用户批准**。
6. **CJ 本地化 + Qdrant 边界**：中文投影在派生 SQLite；**绝不碰 Qdrant**（内存里记录为活跃约束）。
7. **字节口径 vs 字符口径**：判 >64KB 一律用 `len(value.encode('utf-8'))`，别用 SQLite `LENGTH()`。
8. **坏数据默认 fail-fast**：迁移脚本遇非法 UTF-8 / malformed JSON 默认中止；只有 `--skip-bad-rows` 才跳过并落清单，禁止静默丢数据。
9. **asyncmy 读缓冲 bug 会伪装成字符集错误**（M10 实测，接手必读）：报错形如
   `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xfc`，看着就是 latin1/utf8mb4 问题，
   **但服务端字符集可能全是 utf8mb4、max_allowed_packet 也没超限**。真实链条是
   `get_buffer → BufferError: Existing exports of data: object cannot be re-sized` → 读缓冲
   resize 失败 → 协议错位 → 后续行解出垃圾字节（0xfc 是垃圾，不是 latin1 的 ü）。
   **改 charset 无效，唯一有效手段是缩小读回分片**。安全阈值实测：**256KB 过，512KB 挂**
   （1MB 只是"CJ 数据刚好能过"，不是安全值）。
10. **别把大 payload 取回客户端**：需要比对大列时用服务端 `SHA2(col, 256)` + `LENGTH(col)`，
    比把整列读回 Python 快一个数量级，且天然绕开第 9 条。参照
    `scripts/verify_snapshot_migration.py`。
