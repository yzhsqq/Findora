# 共享网关配额验证（2026-09-09）

多个 worker 各用进程内 `GatewayThrottle` 时，总请求并发会随进程数增加。本轮新增 `RedisGatewayThrottle`，将并发占位和请求开始间隔放进同一 Redis Lua 判定，同一个网关/模型 scope 的实例共用上限；无 Redis 部署继续使用原本的进程内限流。

## 接口与实现

```python
RedisGatewayThrottle(
    cache.client,
    max_concurrency=settings.llm_max_concurrency,
    min_interval_seconds=settings.llm_min_interval_seconds,
    namespace=f"{settings.llm_base_url}\n{settings.llm_model}",
)
```

`slot()` 与现有模型包装器的手动 `__aenter__` / `__aexit__` 调用兼容。配额按传入 namespace 的 SHA-256 分组，Redis key 不包含明文 URL、模型名或 API key；各相关 key 使用相同 hash tag。不同部署需要完全一致的 namespace 和配额配置才会共享；若配置不一致且旧范围仍有效，拒绝放大配额。

- 并发占位使用 ZSET，member 为每次调用独立的随机 owner，score 为 Redis TIME 得到的到期时间。原子清理过期 member、检查容量/间隔、加入新占位；并发和间隔均由 Redis 统一判定，不依赖各 worker 的墙上时间一致。
- 默认租期 30 秒、心跳 10 秒；heartbeat 只能续期仍存在且未过期的 owner，不会恢复已被接管的名额。进程消失后不续租，占位到期可回收。
- 默认总等待上限 120 秒、单次 Redis 操作超时 5 秒。Redis 出错时 fail closed，不调用上游，也不退回各进程各算一份配额。运行中失租先置 invalid，再取消当前请求 task。
- 配额一直持有到实际流结束。`StreamFinalizer` 在开始读流时调用可选 `bind_current_task()`，将丢租取消目标移交给实际消费流的 task；提前中止时关闭上游并释放 slot。旧 owner 的 release 只删除自己的 member，不会释放另一请求名额。
- 已安装的 AgentScope 使用 `inspect.isasyncgen()` 识别模型流，因此保留原生异步生成器，返回前只消费内部启动标记、不预读首 token，让 finally 提前生效。即使调用方尚未开始消费就 `aclose()`，也会关闭 SDK 各层包装器和实际 HTTP stream；取消发生在取得流与开始读流之间时，由拥有者 task 的取消回调执行显式清理，不依赖垃圾回收。正常结束的创建者仍可把流交给另一个 task。
- 保留本地 Semaphore，减少单进程大量等候请求对 Redis 的争抢；全局边界由共享 Lua 保证。名额释放后保留最后一次开始时间，短请求同样不能绕过间隔限制。

## 真实验证

从工程根运行：

```bash
FINDORA_REDIS_SERVER_BIN=/tmp/globex-redis-build/redis-7.4.8/src/redis-server \
  uv run python -m pytest -q \
  tests/test_shared_throttle.py tests/test_phase4_throttle.py \
  tests/test_phase4_model.py tests/test_model_cancellation.py tests/test_model_stream_lifecycle.py \
  --junitxml=/tmp/globex-redis-build/throttle-tests.xml
```

实际结果 **41 passed in 5.08s**。其中共享配额 11 项、流生命周期 3 项使用独立启动的官方 Redis 7.4.8；没有使用 fake Redis 代替真实原子命令。模型场景保留实际 `ThrottledChatModel`/AgentScope 包装器，生命周期测试还保留 OpenAI 客户端和 SDK 解析链，仅在 HTTP 传输层注入可关闭 SSE 流，不调用付费网关。Redis 编译和隔离进程细节见《队列重投验证-2026-09-09.md》。未提供 Redis 二进制时这 14 项会明确 skip；另一个未启动流关闭测试使用本地闸门。

最终将这些测试与全部队列相关测试合并运行，结果为 **88 passed in 9.11s**，报告 `/tmp/globex-redis-build/queue-throttle-tests.xml`。

| 取得流后、首 token 前取消 | 保留流强引用仍会关闭连接和释放名额，不依赖垃圾回收 |

## 边界

1. 验证使用单机真实 Redis 与多个并发实例，没有验证生产网关计费、Redis 故障转移或多机网络分区。只有使用同一 Redis、同一 scope 的调用受共同上限约束；其他应用绕过此闸门调用网关的用量不在内。
2. 当前包装器的 quota 范围是一轮模型调用，重试/退避/备用模型在同一 slot 内。它能限制同时在飞的逻辑调用，但不是严格按每次 HTTP retry 重新检查实际请求起点；备用模型也沿用主模型的 scope。若供应商按实际模型/密钥/每次 retry 单独记账，需进一步在每次 upstream attempt 选择正确 scope；不能把当前实现声称为供应商账单的精确配额器。
3. 上游在客户端断连后是否停止服务端计算取决于网关。失租取消和关闭流可防止应用继续消费，不等价于撤销已经产生的模型费用。
4. 调用方应消费或显式关闭返回流；即使从未迭代也支持 aclose，取消/异常结束会主动清理。若正常完成的创建者既不消费、不关闭，也不将流交给消费者，这仍属于未履行资源所有权契约；不能只靠垃圾回收保证任意被丢弃对象的即时释放。
5. 在配额实际可用前取消等待，不会调用上游。Lua 返回已取得名额但响应丢失时会用同一随机 owner 尝试清理；Redis仍不可达则等待租期回收。实例间不保证等待者公平 FIFO。
