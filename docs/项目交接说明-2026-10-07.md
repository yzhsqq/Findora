## 1. 项目背景与目标

**Findora** 是一个面向跨境电商选购场景的全栈 Agent 实战项目：买家用自然语言描述需求（如「预算 300 元以内，帮我找一个寄到中国的轻便背包」），Agent 完成需求理解 → 商品检索 → 方案比较 → 交易确认，页面实时展示过程与结构化商品卡。

技术栈：Python 3.11–3.13 + FastAPI/Uvicorn、AgentScope 2.x、AG-UI + SSE、React 18 + TypeScript + Vite、Qdrant（向量）、HTTP Reranker（精排）、SQLite/Redis、OpenTelemetry + Langfuse（可选）。架构为 DDD 洋葱分层，统一在 `app/composition.py` 装配。

**近期目标（本轮交付主题）**：把商品来源从单一 CJdropshipping 快照扩展为 **CJ + Amazon 美国站 + eBay 美国站三平台联合检索**，要求新平台与 CJ 完全同等待遇——独立快照、独立中文展示、独立向量集合、同一套混合召回链路，且不破坏已有 CJ 行为与购买边界。

**边界（贯穿所有平台的硬约定）**：
- 三平台商品都**只在本地快照**里，页面与检索不实时访问 CJ/Amazon/eBay。
- **只有 CJ 支持站内结算**（本地订单 + 库存事务 + 人工确认）。Amazon / eBay 只能跳转各自原页面，绝不调用 CJ 详情、运费或下单接口。
- 缺失报价展示「报价待核实」，不补造价格、不显示为免费。
- 未取得跨境运费/税费前，不生成「到手价」承诺；决策单里的估算值必须标注为规则估算。

### 3.3 已知问题与待办
1. **正式检索与 Agent 质量门禁仍有未通过项**（见 `docs/正式release验证记录-2026-09-09.md`）；Hybrid 检索收益未证明，不作为效果承诺。
2. **跨平台同款映射缺失**：`canonical_product_id` 仍保留来源编号，三平台条目只是「同类候选」，**不能宣称同款最低价**。需按 GTIN/MPN、品牌型号、规格件数建立人工核验的同款关系。
3. **跨境费用未知（尤其 eBay/Amazon）**：`ships_to` / `excludes_shipping` 只是页面文案，未解析为可配送国家列表；运费、税费、时效未取得，因此不能生成到手价承诺。
4. **库存不对外承诺**：Amazon/eBay 的 `stock_known=false`、规格库存 0，页面可售数量不作为库存暴露。
5. **eBay 数据规模小且无采集时间**：仅 40 条（玩具与爱好 39、收藏品与艺术 1），导入器以文件修改时间（UTC）作为整批 `updated_at`。
6. **启动期全量向量同步会阻塞**（与 CJ 同行为）：首次建库耗时取决于 embedding 服务；指纹增量，重启只补新增/变更。
7. **外部账户欠费会直接表现为 embedding 超时/400**：本轮已遇到 DashScope 欠费导致 Amazon 最后 320 条失败，充值后重启即补齐。**排查类似故障时先看账户状态，不要先怀疑数据**。
8. **本地 Qdrant 有目录进程锁**：本机模式必须单后端进程；多平台集合各用独立 `local_path`（`data/qdrant_amazon`、`data/qdrant_ebay`）避免抢锁。
9. `data/` 下遗留大量历史评审/采集产物（chrome/edge 抓取、cdp 快照、各类 `*.log`/`*.pid`），**不要通过删除 `data/` 解决启动问题**。
10. `scripts/start_local.ps1 -BackendOnly` 曾误报已死的前端 PID（已修复为仅复用存活 PID，否则输出 0）。
11. **Qdrant 集合名与向量点 ID 仍用 `globex_` 前缀（已知并接受）**：改名必须删除重建集合并重算 embedding（CJ 10007 + Amazon 2320 + eBay 40 ≈ 12367 条，约 40–60 分钟且产生费用），因此决定保留。影响：`QDRANT_COLLECTION` 默认值、`CATEGORY_KB_COLLECTION` 默认 `globex_category_kb`、`app/infrastructure/vector/qdrant_product_index.py` 的 uuid5 命名空间 `globex/product/`、历史评测 manifest 里的集合名，全部维持原样。**不要为了「名字统一」单独改这些默认值**：改了但集合没重建，会直接导致向量检索落到空集合而降级为关键词召回。

**三平台检索主链路**（接手方最需要理解的调用链）：

```text
GET /commerce/catalog?platform=...   浏览/编号精确匹配（不 rerank）
Agent 检索 → CatalogSearchUseCase/CJCatalog ─┐
             AmazonCatalog ──────────────────┼→ MultiPlatformCatalog
```

- 商品编号前缀：`CJ=数字 pid`、`Amazon=amazon:us:<ASIN>`、`eBay=ebay:us:<item id>`，据此路由到各自目录；编号查询走精确匹配，不进向量召回。
- 向量不可用时：各平台回退本地关键词召回，结果标记 `degraded_from`，**不会返回空结果**。
- 索引文本一律**原始英文**（标题/品牌/类目/要点/描述前 600 字符，截断 1200），中文只写 `*_localization.sqlite3`，不进向量库。

## 6. 重要决策与注意事项

1. **「原始英文入向量库、中文只做展示」**：中文是展示层投影，写 `*_localization.sqlite3`，绝不写入 Qdrant。dense 跨语言匹配已经能支撑中文查询命中英文商品，BM25 覆盖英文词面。
2. **一平台一集合**：CJ/Amazon/eBay 各自独立 Qdrant 集合，绝不混写；eBay/Amazon 集合还带独立 `local_path`，避免两个嵌入式客户端抢同一目录。
3. **rerank 全局只调一次**：接入多平台后，`CJCatalog` 的 reranker 被置空（`composition.py`），由 `MultiPlatformCatalog` 在合并后统一精排一次，避免重复计费与排序口径漂移。
4. **故障不伪装成「没有商品」**：平台检索失败返回 `partial_results` + `source_status`；向量不可用回退关键词并标记 `degraded_from`；报价缺失显示「报价待核实」。
5. **购买边界不可越线**：只有 CJ 有站内下单/库存/确认；Amazon、eBay 只跳转原页面。决策报告不使用样例关税/物流规则为 Amazon/eBay 生成到手价。
6. **事实优先于流畅**：本地化流水线带事实检查，反复未通过就保留英文原文（`skipped=N`），不要为「全中文」牺牲准确性。
7. **交易账本不可降级到内存**：持久化失败时拒绝启动（避免返回虚假成功）；订单/库存走数据库事务 + 幂等。
8. **语义缓存 key 含模型名 + prompt 指纹**：改 `app/application/prompts/findora.yml` 或换模型后旧回复自动失效。
9. **排查外部故障的顺序**：先看账户/配额（欠费会伪装成超时或空错误），再看服务可达性，最后才怀疑数据；本轮 Amazon 同步卡顿的真实原因就是账户欠费。
