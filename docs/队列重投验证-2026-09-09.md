# 队列重投验证（2026-09-09）

本次将原先只提供辅助方法的 pending 回收接入真实消费循环，并补全双流来源、任务终态、续租与会话串行约束。验证使用官方 Redis 7.4.8 的真实进程；业务模型使用轻量替身，不发起付费模型请求，也不创建订单。

## 实现与数据约定

- `RedisStreamTaskQueue.consume()` 同时回收普通流 `findora:intents` 与大请求流 `findora:intents:large`。领取信封包含 `stream`、`message_id`、`payload`、`deliveries`，ACK、重投与 DLQ 保留原始来源。每条流按剩余槽位单独领取，保证两个流合计并发不超过 `concurrency`。
- enqueue 用 Lua 原子创建 queued 状态和 XADD。Lua 内先 XADD 再写状态，避免 Redis 流类型错误时因脚本不回滚而留下幽灵 queued；消费者在脚本结束前看不到中间状态。同一 `task_id` 不会重复排队；请求指纹随状态保存，运输字段 `enqueued_at`、`priority`、trace 关联字段不参与指纹。相同 ID 改变需求、买家或其他请求语义会被拒绝。
- API 的显式 `request_id` 与买家、会话共同确定任务身份；没有 `request_id` 时，即使文本相同也创建新任务。同步、异步接口均将请求内容冲突转换为 HTTP 409。`_await_result()` 只返回指定 task 的持久化终态，会话事件仅用于唤醒。
- worker 同时持有消息、task、session 三类 Redis 租约。续租在 Redis 内核对 owner；对活动 pending 执行 XCLAIM JUSTID 重置 idle，不增加投递次数。网络异常、租约过期或所有权丢失时先使 `persistence_guard` 失效，再取消 handler；消息不 ACK。
- 正常成功才写 done 并 ACK；一般错误写 retrying 并保留 pending。默认第三次失败后原子写入 DLQ、failed 和 ACK。超过最大次数但尚未执行的消息也进入 DLQ。已经 done/failed 的任务只 ACK，不再次运行 handler；旧 queued 更新不能覆盖 running/终态。
- `execute_intent_task()` 将 `orchestrator.error` 作为失败处理，调用时带 `fresh_session=True` 与租约检查回调。编排器装配同一个 `session_lease`，direct API、AG-UI 和 worker 共用会话互斥；worker 内嵌调用复用已有有效租约。拿到租约后清理旧会话缓存并加载存储快照。

默认参数为：消费并发 1（worker 使用 `WORKER_CONCURRENCY`），最大投递次数 3，stale idle 60 秒，租期 30 秒，心跳约 10 秒。direct 会话租约默认最多等待 30 秒。队列构造/消费方法允许显式传入测试或运行参数；本轮没有新增环境配置项。

## 实际运行

本机没有现成 `redis-server`，Docker 未启动。因此从官方 `https://download.redis.io/releases/redis-7.4.8.tar.gz` 下载源码，只在 `/tmp/globex-redis-build` 编译，没有安装系统服务。可复用已有 Redis 6.2+ 二进制；本次实测版本为 7.4.8。

```bash
make -C /tmp/globex-redis-build/redis-7.4.8/src -j4 BUILD_TLS=no MALLOC=libc redis-server redis-cli

FINDORA_REDIS_SERVER_BIN=/tmp/globex-redis-build/redis-7.4.8/src/redis-server \
  uv run python -m pytest -q \
  tests/test_queue_reliability.py tests/test_queue_api.py \
  tests/test_phase4_queue.py tests/test_harness_infra.py \
  --junitxml=/tmp/globex-redis-build/queue-tests.xml
```

以上命令从工程根运行。测试自行创建 `/tmp/gbx-redis-*` 目录并启动 port 0 的 Redis，只开放权限 700 的 Unix socket，关闭 RDB/AOF。每次测试只清理这个新建实例，结束后关闭进程并清理目录，不读取或清空用户已有 Redis。缺少二进制时测试明确 skip；skip 不等于通过真实 Redis 验证。归档环境的 pytest 脚本 shebang 曾指向旧路径，因此这里固定使用 `uv run python -m pytest`。

首轮结果为 **46 passed in 5.98s**，随后追加流类型错误不能产生幽灵 queued 的回归。最终队列相关共 **47 项通过**：`test_queue_reliability.py` 15 项、`test_queue_api.py` 7 项使用真实 Redis，另外 25 项为已有队列/基础设施契约测试。加上共享配额与 SDK 流生命周期的完整验证为 **88 passed in 9.11s**，最终 JUnit 报告位于 `/tmp/globex-redis-build/queue-throttle-tests.xml`。临时报告不会随仓库持久保存。

## 保证边界与后续项

1. 队列仍是至少一次投递。任务成功与业务写入不是一个跨系统事务；如果副作用完成后进程在 done 前退出，消息可能重放。因此写工具必须另有 prepare/显式确认/持久化幂等。上述队列测试不替代交易并发测试。
2. 后续同轮已实现终态归档、所有消费组 ACK 校验和逐 ID 安全删除，Redis 保留永久小墓碑，见《队列安全归档与Redis重启验证-2026-09-09.md》。默认由运维命令显式 apply；非终态状态及指纹仍为 1 小时 TTL，超长排队需独立保留期限设计。
3. Redis owner 校验对任务状态、ACK、DLQ 和续租是原子的。同轮 SessionStore 已增加持久 epoch/revision CAS 与 owner 绑定，失去最新 claim 的快照不能覆盖新 owner；该机制不是 Redis 与数据库间的分布式事务，业务副作用仍需独立持久幂等。
4. 同轮已补官方 Redis AOF + SIGKILL 重启后双流 PEL/reclaim 验证；仍未宣称覆盖多主故障转移、Redis 网络分区、生产磁盘故障或 Redis Cluster。Lua 当前跨多个 key，生产方案按单 Redis 实例使用；Cluster 需要先统一 hash tag/分片边界。
5. 同会话互斥保证串行，但不承诺多个 worker 的同会话任务严格 FIFO。正常流优先领取，大请求流在持续饱和流量下的公平性还需要容量压测。收到普通退出信号先停止领取并等待在途任务；外部取消会留 pending，未增加强制退出截止时间。
6. 自动租约恢复依赖事件循环及时执行心跳。丢租时请求会取消且不会降级到无锁执行；外部模型服务是否停止计算取决于其断连语义。生产 Redis 的连接超时、持久化和监控配置仍需按部署环境验证。
